# Estrategia de pruebas

> Decisión del usuario (2026-11-20): en las sesiones de trabajo, las pruebas existen **para dar feedback a los agentes de IA**. Los tokens se invierten en features; la regresión completa la ejecuta el CI y lo demás se verifica a mano con las guías de [`Test-manuales/`](Test-manuales/README.md).

## Niveles

| Nivel                      | Qué cubre                                                                                                                                                            | Quién lo ejecuta                          | Cuándo                                                                                         | Comando (en `app/`)                                  |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **1 · Críticos**           | El flujo principal de punta a punta: Inicio → Biblioteca → Añadir canción → Letra → Editor → Reproductor. Pocas pruebas, estables y rápidas, etiquetadas `@critico`. | Agentes                                   | Al terminar una tarea que toque `main/`, `preload/`, `shared/` o una vista del flujo principal | `npm run test:e2e:criticos`                          |
| **2 · De la feature**      | Tests unitarios relacionados con los archivos cambiados y specs E2E creadas o modificadas en la tarea.                                                               | Agentes                                   | Durante y al terminar cada tarea                                                               | `npm run test:cambios` · `npm run test:e2e:cambios`  |
| **3 · Regresión completa** | Toda la suite Vitest y todos los E2E (secundarios incluidos) en Windows, macOS y Linux.                                                                              | CI de GitHub (`.github/workflows/ci.yml`) | En cada push y PR a `develop`/`main`, y en el PR borrador de la fase                           | — (CI)                                               |
| **4 · Manual**             | Lo que no conviene automatizar o necesita hardware real: dos pantallas, audio por HDMI, Wayland, sensaciones de uso, capturas.                                       | Usuario                                   | Al cerrar la fase o la feature                                                                 | Guías en [`Test-manuales/`](Test-manuales/README.md) |

Siempre, antes de dar una tarea por terminada: `npm run typecheck`, `npm run lint` y `npm run format:check` (baratos y sin ejecutar la app).

### Pruebas críticas y secundarias

- **Críticas** (`@critico`): solo las del flujo principal. Viven en `app/e2e/criticos/` y las mantiene el agente `qa`. Si un crítico falla, la tarea no está terminada.
- **Secundarias**: el resto de los E2E (`app/e2e/*.spec.ts`), que prueban features que usan esas pantallas (temas, separación con errores, YouTube, layout del editor, etc.). Los agentes no las ejecutan en bloque: solo las que su tarea crea o modifica (nivel 2). El CI las ejecuta todas (nivel 3).

### Comandos de feedback

| Comando                                     | Qué hace                                                                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run test:cambios`                      | `vitest run --changed`: tests unitarios afectados por los cambios sin commit (incluye los que importan archivos cambiados). Con otra base: `npx vitest run --changed <ref>`. |
| `npm run test:e2e:criticos`                 | Compila y ejecuta solo los E2E con la etiqueta `@critico`.                                                                                                                   |
| `npm run test:e2e:cambios`                  | Compila y ejecuta solo las specs E2E cambiadas sin commit (`playwright test --only-changed`). Con otra base: `npx playwright test --only-changed=<ref>`.                     |
| `npx playwright test e2e/<archivo>.spec.ts` | Una spec concreta, tras `npm run build`.                                                                                                                                     |

## Reglas para los agentes

1. **Feedback, no cobertura.** Escribe el test más pequeño que te diga si lo que implementas funciona. Prefiere Vitest (lógica pura, `main/`, componentes con dobles) a E2E.
2. **E2E solo si aporta feedback que Vitest no da**: integración real entre procesos o ventanas, protocolo, IPC por rol, arranque. Una spec por feature como máximo, con los escenarios imprescindibles.
3. **No ejecutes la suite E2E completa ni `npm test` completo** salvo que el usuario o la sesión principal lo pidan. La regresión es del CI.
4. Si un test ajeno falla en `test:cambios`, comprueba si lo rompe tu cambio. Si no es tuyo (entorno, inestabilidad), anótalo en las notas de la tarea y sigue.
5. Lo que solo se puede comprobar a mano (hardware, varios monitores, sensación visual) **no es una tarea de agente**: se añade a la guía manual de la fase en `Test-manuales/`.
6. Las capturas de revisión visual solo se toman cuando la spec UX las pide para una revisión del diseñador.
7. **Reintentos de foco con `requestAnimationFrame`**: los que viven a nivel de módulo (p. ej. `enfocarCuando`) sobreviven al test que los lanzó y pueden robar el foco al siguiente. Mantén un solo enfoque pendiente a la vez y no dependas en una prueba de reintentos de otra.
8. **Specs con sesión de reproducción abierta**: no cierres la app con `app.close()` (main pide confirmación de salida, 0189, y la prueba agota el tiempo en el `finally`, también en macOS). Usa `salirSinConfirmar(app)` de `e2e/salir.ts`.
9. **Texto solo para lectores de pantalla**: usa siempre la clase compartida `soloLector` de `componentes/componentes.module.css` (en otro módulo, `composes: soloLector from '…/componentes.module.css'`). No copies `position:absolute; width:1px; height:1px` sin `top:0; left:0`: su posición estática cae al final del flujo y añade 1 px de scroll de página (regresión de las fases 4 y 6, vista en el CI de `alpha-2`). La suite crítica comprueba `scrollHeight ≤ innerHeight` en la Biblioteca y en el Editor; si falla, busca el último elemento oculto del documento.
10. **Captura 4K en Linux sin GPU**: `exportacion-captura.spec.ts` omite 3840×2160 solo en Linux y solo si la captura sale a lo sumo 2 px menor (Xvfb con GPU por software da 3839×2159). Se comprueba a mano en Linux real con GPU (guía manual de la fase 6).
11. **Efectos pasivos de React en pruebas de componente**: el foco inicial y los efectos de montaje (p. ej. `Escucha` pausa lo que no es la pista activa) se vuelcan en diferido y, bajo carga, caen después de que aparezca el texto o incluso después de un clic. Antes de interactuar con algo cuyo montaje tenga efectos, vacíalos con `await act(async () => {})`; y comprueba el foco con `await waitFor(() => expect(…).toHaveFocus())`, no en síncrono (fallos intermitentes de `Progreso.test.tsx` en alpha-2).
12. **Medir diálogos que cargan datos**: un diálogo como el de impacto del tema se abre en «calculando» y crece cuando llega el impacto; espera a un texto del cuerpo ya cargado antes de medir cajas (`botonesDentroDelDialogo`), o compararás la caja pequeña con botones ya recolocados (fallo de `temas-editor` «tres acciones», alpha-2). Los atajos del editor también se registran en un efecto pasivo: tras `findBy…`, `await act(async () => {})` antes de `fireEvent.keyDown` (regla 11). `conTemas` cierra con `salirSinConfirmar`: un `app.close()` con un diálogo/borrador abierto se cuelga y enmascara el error real como «1 error was not a part of any test».

## Regresión en el CI

- Cada fase abre pronto un **PR borrador** de `fase/0.2.0-N-…` a `develop`; cada push ejecuta `ci.yml` completo.
- La sesión principal lee los fallos (`gh run list`, `gh run view --log-failed`) y el agente `qa` los clasifica: regresión de la fase (vuelve a la tarea responsable), inestable (se marca y se corrige aparte) o de entorno.
- Los criterios de cierre de la fase exigen el CI en verde, no ejecuciones locales completas.

## Responsables

- **`qa`**: mantiene los críticos y esta estrategia, clasifica fallos del CI, escribe las guías manuales y propone qué pruebas de feedback necesita cada tarea. Ver `.claude/agents/qa.md`.
- **`arquitecto`**: en cada tarea indica en «Pruebas de feedback» los tests mínimos y qué va a la guía manual.
- **`programador`**: escribe y ejecuta las pruebas de feedback de su tarea (niveles 1 y 2).

## Fallos conocidos clasificados

- `editor-layout.spec.ts` › «con la barra vertical de main a 1024 px de ancho no se salta a la disposición B» (2026-11-22, 0.2.2): **dependiente de plataforma**. Falla en macOS con `la barra vertical ocupa ancho: Expected > 0, Received 0` porque macOS usa barras de desplazamiento superpuestas (`offsetWidth - clientWidth` = 0). No es un defecto de la app ni de 0.2.2; la prueba asumía barras clásicas (Windows, Linux). Se omite ahora en macOS cuando la barra no ocupa ancho (`test.skip`); el resto de comprobaciones de la prueba (`bajo === 'alto'`, sin scroll horizontal) las cubre el CI en Windows y Linux. El «tooltip a los 500 ms» no falló en esta ejecución: sigue marcado como intermitente.
- `ventana.spec.ts` (2026-11-22, 0.2.2): **de entorno**. En un Mac Retina falla con `devicePixelRatio` = 2 (espera 1) o con el viewport limitado por la pantalla (1280 × 763 en lugar de 1024 × 576). No cambia con 0.2.2 (`main/index.ts` no toca el tamaño de ventana respecto a v0.2.1). El CI (sin Retina) lo cubre.
- `editor.spec.ts` › «los marcadores previsualizan, cancelan y guardan un único paso» (línea 410, 2026-11-22): **intermitente de la prueba**. Un fallo (línea 430, el segundo arrastre no movió el inicio: 2000 en lugar de 2800 ± 45) y 0 en unas 45 ejecuciones (10 en paralelo, 10 con un trabajador, 3 × `editor` + `letras` con 2 trabajadores, regresión completa). El arrastre no cambió desde v0.2.1. Causa probable: el segundo arrastre empieza justo tras `Escape` + `mouse.up()` con la caja del marcador medida antes de asentarse el diseño. Si reaparece, envolver ese arrastre en `expect(async () => …).toPass()`.
- `reproductor.spec.ts` › «la pantalla final vuelve sola al terminar la cuenta atrás» (línea 252, 2026-11-22): **intermitente bajo carga** (falló una vez junto a `exportacion`, `fase5` y `temas-editor` con 4 trabajadores; 5 de 5 en solitario y pasó en la regresión completa). Dura 12-16 s con el tiempo de 30 s.
- Vitest, **inestables bajo carga** (2026-11-22; solos pasan siempre y la suite completa sola pasa: 3749 de 3749): `Biblioteca.agrupacion.test.tsx` B7 y `sesion/sesion.test.tsx:269` (vistos antes, **no reproducidos** en 11 ejecuciones nuevas; causa probable: efectos pasivos y `requestAnimationFrame` diferidos, reglas 7 y 11); `Editor.comprobar.test.tsx` F4-E3/E5 (tiempo de 5000 ms; la prueba tarda 1,2-1,4 s sola) y F4-E7 (`findBy` de 1 s), que con tres suites completas a la vez fallaron en 6 de 6 ejecuciones junto a `Editor.temas.test.tsx` (T2b, T1, T4–T5, T7), `Editor.test.tsx` («menos de 100 opciones»; F «vacía el guardado…») y `LetraElegida.test.tsx`: **intermitentes de carga, no regresión**. Pregunta [0208](preguntas/0208-pruebas-de-componente-del-editor-fragiles-bajo-carga.md) pide subir sus tiempos. `main/fuente/archivo.test.ts` («cancelar a mitad no deja carpeta ni procesos», «importar dos veces…») falla solo si hay varias suites a la vez (cuenta procesos del sistema): **no lances dos `vitest` a la vez**.
- Regresión local completa de la entrega alpha.1 (2026-11-22, Mac M1): 203 pasan, 43 omitidas (opt-in y red), 1 falla (`ventana.spec.ts`, de entorno). Críticos 1 de 1. Los críticos no cambian con las features 1, 2 y 4: el flujo principal no añade pasos obligatorios (la comprobación es opcional y la letra en pantalla solo cambia lo que se ve).
- **Los críticos cambian con la feature 5 (alpha.2)**: con «Buscar la letra automáticamente» activo (valor por defecto) añadir una canción la deja sola en «Lista para revisar»; «Revisar» abre la revisión guiada y «Marcar como lista» sigue siendo del usuario. ## Regla: sin red real en las pruebas (2026-11-22)

Desde la preparación desatendida (0308), **añadir una canción lanza solo la búsqueda de letra** a LRCLIB (título, artista, álbum y duración). Un E2E que añada una canción sin fijar `SHINOBI_LRCLIB_URL` saldría a lrclib.net con los datos del fixture. Cómo se cumple:

1. **Barrera por defecto** (`app/e2e/preparar-electron.ts`, `globalSetup` de Playwright): si `SHINOBI_LRCLIB_URL` no viene definida, arranca un **sumidero** local (127.0.0.1, puerto libre) que responde 503 a todo y guarda lo que recibe en `GET /__sumidero`, y fija la variable a su dirección. Los workers la heredan y todos los `electron.launch` de `e2e/` construyen su `env` con `...process.env` (comprobado: 28 bloques `env: {` y los `env` sueltos de `seguridad.spec.ts`, `sesion-main.spec.ts` y las specs `*-red`). Cada spec que necesita su doble lo fija en su `env` (sobreescribe el sumidero).
2. **Segunda barrera**: el `globalSetup` fija `SHINOBI_E2E=1`; con la tarea 0372 el producto, sin empaquetar y con esa variable, nunca usa la URL real de LRCLIB (búsqueda y `HEAD` de comprobación de conexión).
3. **Opt-in de red** (`letras-red.spec.ts`, `youtube-red.spec.ts`, con `SHINOBI_TESTS_RED=1`): borran `SHINOBI_E2E` (y `SHINOBI_LRCLIB_URL` la primera) de su `env` de forma explícita.
4. **Vigilante**: `e2e/sin-red-real.spec.ts` (secundaria, 2 pruebas, ~5 s) comprueba que la configuración por defecto apunta a un sumidero local, que `SHINOBI_E2E` vale `1`, y que añadir un WAV con la configuración por defecto (búsqueda automática activada) hace llegar la petición al sumidero y solo a él; arranca además con `--host-resolver-rules` que no resuelve ningún nombre que no sea 127.0.0.1. No se omite si falta el sumidero: falla.
5. **Privacidad con el interruptor apagado** (0.2.2): `importar-archivo.spec.ts` y `importar-youtube.spec.ts` ponen `preparacion.automatica` a `false`, fijan `SHINOBI_LRCLIB_URL` a un doble que cuenta **todas** las peticiones (también `HEAD`) y esperan 0 tras añadir. Con una descarga de YouTube sin conexión, la comprobación de conexión de la cola (`HEAD` a las 60 s) sí sale aunque el interruptor esté apagado (pregunta [0243](preguntas/0243-comprobacion-de-conexion-contra-lrclib-con-el-interruptor-apagado.md)).
6. `e2e-paquete/` (app empaquetada) no añade canciones. Los `uv run pytest` y los Vitest no usan red (las pruebas con LRCLIB real son `vitest run lrclib.red`, opt-in).
7. Quien ejecute Playwright con su propia `SHINOBI_LRCLIB_URL` verá fallar el vigilante: es lo esperado.
